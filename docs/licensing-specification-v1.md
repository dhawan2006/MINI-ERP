# Mini POS Licensing Specification (v1)

## 1. Purpose
The purpose of the licensing system is to enforce commercial software boundaries by cryptographically binding a purchased license entitlement to a specific customer device. 

The core philosophy of this implementation is **offline-first autonomy**. The licensing system exists to protect the commercial interests of the software vendor without penalizing legitimate users with unreliable internet access. 

Explicit directives:
* "Billing remains offline-first."
* "Licensing does not become a network dependency for ordinary POS operation."
Once activated, the system operates completely independently of the network until explicit administrative actions (like deactivation) or the commercial expiry date occurs.

## 2. Terminology
- **License**: The commercial entitlement purchased by a customer.
- **License Key**: A human-readable string (e.g., `ABCD-1234-EFGH-5678`) given to the customer to claim the license.
- **License ID**: The internal canonical UUID representing the license on the server.
- **Customer**: The commercial entity that purchased the license.
- **Device**: A unique cryptographic identity representing a physical machine where Mini POS is installed.
- **Device Key Pair**: A local asymmetrical cryptographic key pair (P-256 ECDSA) generated by the native identity service (e.g., macOS Secure Enclave).
- **Device Public Key**: The public half of the device key pair, shared with the server.
- **Device Private Key**: The secret half of the device key pair, permanently stored in secure native storage (never transmitted).
- **Device Key ID**: A deterministic fingerprint (e.g., SHA-256 hash) of the Device Public Key.
- **Activation**: The one-time online process of binding a Device to a License.
- **Activation Request**: The cryptographic payload sent from the client to claim a license.
- **Activation Request ID**: A client-generated UUID (v4) used for idempotency.
- **Authorization**: The cryptographic proof of entitlement, bounding a Device to a License for a specific duration.
- **Signed Authorization**: The Authorization object digitally signed by the Server.
- **Signing Key**: The Server's private asymmetrical key used to sign Authorizations.
- **Signing Key ID**: A string identifier (e.g., `key-2026-v1`) for the server key used for signature verification.
- **Server / Licensing Server**: The central internet-hosted authority that validates licenses and issues Authorizations.
- **Entitlement**: The specific rights granted (e.g., valid dates, max devices).
- **Valid From**: The ISO 8601 UTC timestamp when the authorization begins.
- **Valid Until**: The ISO 8601 UTC timestamp when the authorization explicitly expires.
- **Issued At**: The ISO 8601 UTC timestamp when the server signed the authorization.
- **Deactivation**: The online process of explicitly releasing a device binding to free up a license slot.
- **Transfer**: The logical operation of deactivating on one machine and activating on another.
- **Reactivation**: Activating the same device identity against the same license.
- **Clock Rollback**: When the local system time is moved backwards to attempt to evade expiry.
- **Replay**: Attempting to reuse a previously sent network request or cryptographic challenge.
- **Idempotency**: The guarantee that repeating a network request (with the same Request ID and payload) yields the exact same deterministic result without side effects (e.g., without double-allocating a license slot).

## 4. Commercial License Model
The License conceptually represents a purchased slot limit and a time boundary.

**Properties:**
- `id`: UUID (Primary Key)
- `licenseKey`: String (Unique index, given to customer)
- `productId`: String (e.g., `mini-pos-pro`)
- `status`: Enum (`ACTIVE`, `REVOKED`, `EXPIRED`, `DISABLED`)
- `validFrom`: UTC Timestamp
- `validUntil`: UTC Timestamp
- `maxDevices`: Integer (default 1)
- `createdAt`: UTC Timestamp

**Statuses & Transitions:**
- `ACTIVE`: Normal operational state.
- `REVOKED`: Administratively cancelled (e.g., refund, fraud).
- `EXPIRED`: Natural time expiration.
- `DISABLED`: Temporarily suspended.

**Legal Transitions:**
- `ACTIVE` -> `EXPIRED` (Natural passing of time)
- `ACTIVE` -> `REVOKED` (Admin action)
- `ACTIVE` -> `DISABLED` (Admin action)
- `DISABLED` -> `ACTIVE` (Admin action)

**Illegal Transitions:**
- `EXPIRED` -> `ACTIVE` (Cannot un-expire without a renewal transaction creating a new Entitlement or extending `validUntil`).
- `REVOKED` -> `ACTIVE` (Revocation is final terminal state).

## 5. Exact Expiry Semantics
Rule: `validFrom <= currentTime < validUntil`
*Explanation:* The authorization is strictly valid from the exact millisecond of `validFrom` up to, but NOT including, the exact millisecond of `validUntil`.

- **One second before expiry**: Application operates completely normally. Billing is permitted.
- **Exactly at expiry**: Billing is immediately blocked.
- **One second after expiry**: Billing remains blocked. 

**Time Representation:**
All timestamps must be canonical ISO 8601 UTC strings with millisecond precision (e.g., `2026-09-28T12:00:00.000Z`). UTC is immune to local timezone configuration changes.

## 6. Device Model
A "Device" is exclusively defined by its cryptographic key pair. It does NOT rely on hardware identifiers (MAC, CPU, UUID) which are brittle, privacy-invasive, and prone to spoofing or changing upon OS updates.

- **deviceKeyId**: SHA-256 hash of the DER-encoded public key.
- **key pair**: P-256 (secp256r1) ECDSA (required for macOS Secure Enclave hardware backing).
- **protected private key**: Stored securely via OS Native Hardware (macOS Secure Enclave).

If the native secure hardware is completely wiped or unavailable, the device identity is permanently lost. The machine is conceptually a "new device" and requires a new key pair and a new activation. We do NOT fallback to insecure file-based storage in production. Development-only flags will mock the Keychain but must be strictly stripped in production.

## 7. Cryptographic Trust Model
**Server Trust:**
- The Server holds a Private Signing Key.
- The Server signs the Authorization payload.
- The Client hardcodes the Server's Public Verification Key(s).
- The Client uses the hardcoded Verification Key to verify the Authorization signature.

**Device Trust:**
- The Device holds a Private Device Key.
- The Device signs a Server-issued Challenge during Activation.
- The Server uses the provided Device Public Key to verify the Challenge.

*They are distinct.* Server signs authorizations; Device signs proofs of possession.

**Specifications:**
- Server Signature Algorithm: Ed25519 (EdDSA).
- Device Proof Algorithm: P-256 (ECDSA). Signature encoded as DER.
- Encoding: Base64URL without padding for signatures and public keys.
- Protocol Version: `1`

## 8. Key Rotation
The Server holds multiple signing keys to allow rotation.
Keys are identified by a `signingKeyId` (e.g., `prod-2026-ed25519-1`).

- **New Key Introduction**: The client binary is shipped with an array of trusted Public Verification Keys, mapped by `signingKeyId`.
- **Client Recognition**: The Authorization object specifies its `signingKeyId`. The client looks up the key.
- **Old Authorizations**: Remain verifiable as long as the old `signingKeyId` remains in the client's trusted array.
- **Key Retirement**: When all authorizations signed by an old key have expired, the old key can be removed from future client updates.
- **Unknown Key**: If the client sees an unknown `signingKeyId`, verification FAILS immediately.

## 9. Activation Flow
1. **USER**: Inputs `licenseKey` and clicks Activate.
2. **CLIENT**: Syntactically validates license key format.
3. **CLIENT -> IDENTITY**: Requests `deviceKeyId` and `publicKey`. Generates if missing.
4. **CLIENT -> SERVER**: HTTP POST `/api/v1/activation/challenge` (payload: `deviceKeyId`).
5. **SERVER**: Returns a random cryptographic challenge.
6. **CLIENT -> IDENTITY**: Requests signature of the challenge using Device Private Key.
7. **CLIENT**: Generates `activationRequestId` (UUIDv4).
8. **CLIENT -> SERVER**: HTTP POST `/api/v1/activation` (payload: `licenseKey`, `publicKey`, `challengeSignature`, `activationRequestId`).
9. **SERVER**:
    - Verifies `challengeSignature` against `publicKey`.
    - Looks up License.
    - Checks device count constraints.
    - Binds `deviceKeyId` to License (database transaction).
    - Generates signed `Authorization` object.
10. **SERVER -> CLIENT**: Returns signed `Authorization`.
11. **CLIENT**: Verifies `Authorization` signature using trusted Server Public Key.
12. **CLIENT**: Writes `Authorization` atomically to local storage.
13. **CLIENT**: Transitions to `ACTIVE` state.

## 10. Device Proof
To prove possession of the Device Private Key:
1. Server creates a 32-byte cryptographically secure random `challenge`.
2. The challenge is tied to a 5-minute server-side expiration cache.
3. Client uses the native identity service to sign the raw `challenge` bytes.
4. Server verifies the signature. The challenge is immediately marked as consumed (single-use) to prevent replay attacks.

## 11. Activation Request Idempotency
- **Generated by**: Client (UUIDv4) right before the `/api/v1/activation` POST.
- **Uniqueness**: Globally unique per activation attempt.
- **Server Memory**: Server remembers the `activationRequestId` indefinitely (or practically 30+ days).
- **Same Request Retry**: If the server sees a known `activationRequestId`, it checks if the exact same payload was sent. If yes, it returns the *exact same* Signed Authorization without decrementing license slots or failing.
- **Conflict**: If the server sees a known `activationRequestId` but a *different* payload, it rejects with `409 Conflict`.

## 12. Concurrency Rules
- **INVARIANT A**: One license cannot exceed its configured active-device limit.
- **INVARIANT B**: One device cannot be simultaneously actively bound to multiple licenses.
- **INVARIANT C**: An activation cannot partially succeed (requires strict DB Transactions).
- **INVARIANT D**: An activation request cannot result in two active bindings because of concurrent network requests.
- **INVARIANT E**: Every successful activation has a corresponding server-side authorization record.
- **INVARIANT F**: Every active device binding belongs to an existing valid license.

**Expected Results:**
- Two computers activate same 1-seat license simultaneously -> One succeeds, one fails with `DEVICE_LIMIT_REACHED`.
- Same computer activating two licenses -> Second attempt fails with `DEVICE_ALREADY_BOUND`.
- Same device retries activation -> Idempotent success.
- Deactivate + Activate concurrently -> Resolved by database row locks. One transaction wins, the second evaluates the new state.

## 13. Server Database Model
Tables:
1. **licenses**
   - `id` (PK)
   - `license_key` (UNIQUE)
   - `status`, `valid_from`, `valid_until`, `max_devices`
2. **devices**
   - `device_key_id` (PK)
   - `public_key`
3. **license_bindings** (Enforces Invariants)
   - `id` (PK)
   - `license_id` (FK licenses)
   - `device_key_id` (FK devices, UNIQUE to enforce Invariant B)
   - Constraint: Count of rows per `license_id` must be `<= max_devices` (Enforced via DB transaction serialization or check constraints).
4. **activation_requests**
   - `request_id` (PK)
   - `payload_hash` (To detect payload conflicts)
   - `response_payload` (To serve idempotent retries)

## 14. Authorization Object
Stored locally as JSON.

```json
{
  "protocolVersion": 1,
  "authorizationVersion": 1,
  "licenseId": "uuid...",
  "productId": "mini-pos-pro",
  "deviceKeyId": "hash...",
  "validFrom": "2026-09-01T00:00:00.000Z",
  "validUntil": "2027-09-01T00:00:00.000Z",
  "issuedAt": "2026-09-28T12:00:00.000Z",
  "signingKeyId": "prod-2026-1",
  "signature": "base64url..."
}
```
**All fields are IMMUTABLE and SERVER-CONTROLLED.** Any client-side modification will invalidate the `signature`. The client is strictly READ-ONLY.

## 15. Canonicalization
Before signing and verifying, the JSON payload must be deterministically serialized:
1. Exclude the `signature` field.
2. Sort keys alphabetically.
3. Remove all whitespace (no spaces, no newlines).
4. UTF-8 encode.
5. Apply Ed25519 signature over the resulting bytes.
*(Equivalent to stable JSON stringification).*

## 16. Local Authorization Storage
- **APPLICATION DATA** (SQLite `database.db`): POS Bills, Products, Settings.
- **LICENSING DATA** (`authorization.json`): The signed JSON payload.
- **DEVICE SECRET MATERIAL**: Native OS Keychain (macOS / Windows).

**Storage Rules:**
- The `authorization.json` is stored in the Electron `userData` directory, separate from the SQLite database.
- It is updated using atomic file replacement (write to `.tmp`, rename to target) to prevent corruption during power loss.
- **CRITICAL**: The SQLite database MUST NEVER contain the Authorization or Device Keys.
- **CRITICAL**: A corrupted or deleted `authorization.json` gracefully falls back to `NOT_ACTIVATED`. It does NOT wipe the SQLite DB.

## 17. Application Startup
```text
START
↓
Load local `authorization.json`
↓
Does it exist and parse as valid JSON?
├── NO → State: NOT_ACTIVATED
└── YES
      ↓
Verify `signingKeyId` is known.
      ↓
Canonicalize and Verify `signature`.
      ↓ (If fail -> State: INVALID_AUTHORIZATION)
Verify `deviceKeyId` matches native OS Keychain public key.
      ↓ (If fail -> State: DEVICE_MISMATCH)
Verify `validFrom <= currentTime < validUntil`
      ↓ (If fail -> State: EXPIRED)
Verify clock rollback detection heuristics.
      ↓
State: ACTIVE
```

## 18. Offline Behavior
**CRITICAL REQUIREMENT:**
When internet is unavailable AFTER successful activation:
- Startup: Evaluates local `authorization.json`. Succeeds.
- Billing: ALLOWED.
- Product Management: ALLOWED.
- History: ALLOWED.
- PDF/Printing: ALLOWED.
- Backup/Restore: ALLOWED.

There is NO periodic network check. There is NO background "heartbeat". The signed authorization is absolute truth until the `validUntil` timestamp. 

## 19. Server Unavailable
- **Activation**: Fails with `SERVER_UNAVAILABLE`. User must retry later.
- **Deactivation**: Fails with `SERVER_UNAVAILABLE`. User cannot transfer license until online.
- **Normal Offline Billing**: 100% unaffected. Billing does not attempt to contact the server, so it cannot know or care if the server is down.

## 20. License Expiry
When `currentTime >= validUntil`:
- **Billing**: BLOCKED (Cannot finalize new bills).
- **Product Management**: ALLOWED (Can view/edit catalog).
- **History**: ALLOWED (Can view past bills).
- **PDF & Printing**: ALLOWED (Can reprint existing bills).
- **Backup & Restore**: ALLOWED.
- **Settings**: ALLOWED.

Users own their historical data forever. Expiry only blocks creating *new* commercial value (new bills).

## 21. Deactivation
- **Who**: The user of the activated device (via the UI).
- **Proof**: Requires signing a Deactivation Challenge with the Device Private Key.
- **Server**: Removes the `license_bindings` row, freeing the slot.
- **Local**: `authorization.json` is deleted.
- **Network Failure**: If the network fails, the local authorization is NOT deleted. It must be an atomic distributed success.
- **POS Data**: Business data (SQLite) is untouched.

## 22. Transfer / Device Replacement
**Normal Workflow**: Old Device -> Deactivate -> Server frees slot -> New Device -> Activate.

**Lost/Broken Old Device**: The old device cannot mathematically deactivate itself. 
Since V1 does not include an administrative web portal, the user must contact Customer Support. Support sets the Server binding to `REVOKED` or forcefully deletes the binding. The New Device can then Activate. 
*(If the Old Device ever boots up again while offline, it will still think it is ACTIVE until expiry, but it can never be renewed or reactivated. This is an accepted tradeoff of the offline-first model).*

## 23. Reinstallation
- **Uninstall/Reinstall (Same OS identity)**: The OS Keychain retains the Device Private Key. `authorization.json` is lost. The user inputs their License Key and clicks Activate. The Server recognizes the same `deviceKeyId`, considers it a Reactivation (idempotent/allowed), and returns a new Authorization. No slots are lost.
- **Machine wipe / New OS**: The OS Keychain is wiped. It is considered a New Device. Follows rules in Section 22.

## 24. Clock Rollback Policy
To mitigate users setting their clock to 2020 to evade expiry:
- The application stores a `lastKnownTrustedTime` timestamp in a hidden local file, updated every time the app starts, finalizes a bill, or successfully syncs with the server.
- If `currentTime < lastKnownTrustedTime`, a Clock Rollback is detected.
- **Behavior**: The application state immediately transitions to `INVALID_AUTHORIZATION` until the clock is restored to `>= lastKnownTrustedTime`.
- No giant time sync subsystem is built. Rely purely on monotonic local time progression tracking.

## 25. Local Authorization Tampering
- **Modified signature**: Verification fails -> `INVALID_AUTHORIZATION`.
- **Changed expiry/license/device**: Signature breaks -> `INVALID_AUTHORIZATION`.
- **Malformed/Truncated file**: JSON parse fails -> `NOT_ACTIVATED`.
- **Unknown schema/protocol**: Fails validation -> `INVALID_AUTHORIZATION`.
- **Unknown signing key**: Fails validation -> `INVALID_AUTHORIZATION`.
The client gracefully fails closed. Business data is unaffected.

## 26. Copy / Clone Attack Model
- **Attack**: User copies `authorization.json` and SQLite database to a friend's PC.
- **Defense**: The friend's PC has a different (or missing) Native OS Keychain. The `deviceKeyId` in the `authorization.json` will NOT match the friend's actual Device Key.
- **Result**: Startup validation fails with `DEVICE_MISMATCH`.
- **Limitation**: If an attacker completely clones the Hard Drive at a block level, including the OS secure keychain partitions, to identical hardware, the OS might serve the same Device Key. We accept this as out of scope for a desktop application.

## 27. Billing Integration Contract
The licensing system exposes a single synchronous boundary to the application state (e.g., Zustand).

```typescript
function isBillingAuthorized(): boolean
```
- **Where**: Evaluated in the Renderer process, backed by state published from the Main process.
- **What it returns**: `true` if `ACTIVE`. `false` otherwise.
- **Network**: NEVER initiates a network request.
- **Knowledge**: The Billing module knows nothing about HTTP, signatures, device keys, or server URLs. It only consumes the boolean.

## 28. Error Model
Errors strictly categorized:
- `ACTIVATION_REQUIRED`: Normal pristine state.
- `LICENSE_EXPIRED`: Time has passed.
- `LICENSE_NOT_FOUND`: Typo in license key.
- `DEVICE_LIMIT_REACHED`: Max seats occupied.
- `AUTHORIZATION_INVALID`: Tampering or parse error.
- `DEVICE_MISMATCH`: File copied to wrong machine.
- `SERVER_UNAVAILABLE`: Network down.
- `ACTIVATION_REPLAY`: Server detected challenge manipulation.
- `CLOCK_ROLLBACK_DETECTED`: Time manipulation detected.

## 29. Security Boundary
- **Renderer**: Knows license status, valid dates. Cannot access private keys or raw crypto.
- **Main Process**: Coordinates HTTP activation, verifies signatures, writes `authorization.json`.
- **Native Identity Service (Node native module/Keychain)**: Generates keys, holds private keys, signs challenge bytes. NEVER exposes private key bytes to Main/Renderer.
- **Server**: Authoritative for business logic, issues signed objects.

## 30. Production vs Development
- **Production**: Strictly verifies against hardcoded `prod` Server Public Keys. Enforces OS Keychain. NO bypass flags.
- **Development**: Reads `VITE_LICENSING_ENV=development`. Uses `dev` Server Public Keys. Mocks the OS Keychain to file-based storage for testing.
Environment variables cannot force a production build to use development keys (enforced at build time via constant injection).

## 31. Licensing State Machine
- `NOT_ACTIVATED`: No authorization found.
- `ACTIVE`: Valid authorization, valid device, valid time.
- `EXPIRED`: Valid authorization, valid device, time expired.
- `INVALID_AUTHORIZATION`: Tampering, clock rollback, or unknown format.
- `DEVICE_MISMATCH`: Authorization belongs to another device.

*Impossible Transitions*:
`EXPIRED` -> `ACTIVE` (Without network reactivation giving a new `validUntil`).

## 32. State Transition Table

| Current State | Event | Condition | Next State | Server Required? | Billing Allowed? |
| :--- | :--- | :--- | :--- | :---: | :---: |
| `NOT_ACTIVATED` | Startup | Auth file missing | `NOT_ACTIVATED` | No | No |
| `NOT_ACTIVATED` | Activate | Valid network response | `ACTIVE` | Yes | Yes |
| `ACTIVE` | Startup | Auth valid & unexpired | `ACTIVE` | No | Yes |
| `ACTIVE` | Startup (Time pass) | `currentTime >= validUntil` | `EXPIRED` | No | No |
| `ACTIVE` | Deactivate | Valid network response | `NOT_ACTIVATED` | Yes | No |
| `ACTIVE` | Tamper File | Signature fails | `INVALID_AUTHORIZATION`| No | No |
| `ACTIVE` | Rollback Clock | `current < lastKnown` | `INVALID_AUTHORIZATION`| No | No |
| Any | Copy to New PC | `deviceKeyId` differs | `DEVICE_MISMATCH` | No | No |

## 33. Security Invariants
- **SEC-01**: Client cannot manufacture a valid server-signed authorization.
- **SEC-02**: Changing signed authorization fields invalidates signature.
- **SEC-03**: A device cannot prove another device's private-key possession.
- **SEC-04**: A replayed challenge cannot be reused successfully.
- **SEC-05**: Duplicate activation requests cannot create duplicate bindings.
- **SEC-06**: Concurrent activations cannot violate database constraints.
- **SEC-07**: Billing does not require internet after successful activation.
- **SEC-08**: License expiry cannot be extended by editing local data.
- **SEC-09**: Deactivation cannot delete POS business data.
- **SEC-10**: Private device-key material never crosses IPC boundaries.

## 34. Data Integrity Invariants
- One active device per license when `maxDevices=1`.
- No authorization without corresponding server license row.
- No successful activation without cryptographic device proof.
- No partial activation transactions (DB level atomic commits).
- No duplicate activation result for same `activationRequestId`.

## 35. API Contracts
**POST /api/v1/activation/challenge**
- *Req*: `{ "deviceKeyId": "string" }`
- *Res*: `{ "challenge": "base64url", "expiresAt": "timestamp" }`

**POST /api/v1/activation**
- *Req*: `{ "licenseKey": "string", "publicKey": "base64url", "challengeSignature": "base64url", "activationRequestId": "uuid" }`
- *Res (200)*: `{ "authorization": { ... } }`
- *Res (4xx)*: `{ "error": "DEVICE_LIMIT_REACHED" }`

**POST /api/v1/deactivation**
- *Req*: `{ "licenseId": "uuid", "deviceKeyId": "string", "deactivationChallengeSignature": "base64url" }`
- *Res (200)*: `{ "status": "ok" }`

## 36. Network Failure Matrix

| Failure Point | Expected Client State | Data Safety | User Message |
| :--- | :--- | :--- | :--- |
| Before request sent | Unchanged | Safe | "Check internet connection." |
| Request sent, no response | Unchanged | Safe | "Server timeout. Please retry." |
| Server commits, response lost | Unchanged | Safe | "Server timeout. Please retry." (Will succeed on retry via Idempotency) |
| Server 500 / 429 | Unchanged | Safe | "Service temporarily unavailable." |

## 37. Crash Matrix
- **Crash before activation request**: Remains `NOT_ACTIVATED`.
- **Crash after server commit**: Server bound the license, but client remains `NOT_ACTIVATED`. Upon next launch, user clicks activate again, idempotency provides the authorization safely.
- **Crash while writing local authorization**: Atomic `.tmp` rename ensures either the old state or the full new state. No corrupted files.

## 38. Backup / Restore Interaction
- **Content**: The Mini POS SQLite Backup system ONLY backs up the SQLite file.
- **Exclusion**: `authorization.json` and Native Device Keys are explicitly EXCLUDED from backups.
- **Restore Behavior**: Restoring a database on a new PC brings all POS data over, but the app will be `NOT_ACTIVATED` because licensing data is not part of the backup. The user must properly Activate the new PC.

## 39. Audit Logging
Server must log:
- Activation attempts (success/fail).
- Deactivations.
- Replay/Tampering rejections.
*(No raw private keys or challenges are logged).*
Retention: 7 years (commercial audit standard).

## 40. Rate Limiting / Abuse
- **Endpoint Protection**: IP-based rate limiting on `/api/v1/activation/challenge` to prevent brute forcing license keys.
- **Account Protection**: Max 10 failed activation attempts per hour per `licenseKey`.

## 41. Versioning / Compatibility
- `protocolVersion`: Defines the HTTP interactions.
- `authorizationVersion`: Defines the JSON schema of the authorization object.
- **Unknown protocol**: Client FAILS CLOSED if it encounters an `authorizationVersion` it doesn't understand (e.g., v2).

## 42. Revocation Policy
Because Option A strictly operates offline, server-side revocation (changing status to `REVOKED` in the DB) takes effect **only if/when the device comes online to perform an administrative action** (like deactivation or reactivation).
- If the device never connects to the internet again, the `REVOKED` license continues to operate locally until its `validUntil` date.
- This is an explicit, accepted business decision to guarantee true offline autonomy.

## 43. Realistic Security Guarantees
**WE CAN STRONGLY PROTECT AGAINST:**
- Casual copying of license files.
- Modifying local authorization (time extension).
- Replay attacks on network requests.
- Renderer process extracting secrets.

**WE CANNOT ABSOLUTELY GUARANTEE:**
- Protection against a highly sophisticated attacker with root access who actively debugs and patches the Electron application binary in memory to force `isBillingAuthorized = true`.

## 44. Threat Model
- **Actor: Normal customer with no internet**. *Impact*: None. *Defense*: Architecture is offline-first.
- **Actor: Person copying files**. *Impact*: Cannot use on new PC. *Defense*: Device Key bound to OS hardware keychain.
- **Actor: Clock manipulator**. *Impact*: Prevented. *Defense*: Monotonic time tracking (`lastKnownTrustedTime`).
- **Actor: Binary patcher**. *Impact*: Can bypass UI logic. *Defense*: Code obfuscation/signing (out of scope for licensing protocol itself).

## 45. Observability
- Client logs `activationRequestId` and `error_codes` to local file.
- Client logs "Authorization signature verification failed" but does not expose expected signature.
- NEVER log `deviceKeyId` or `publicKey` in non-debug levels to protect user privacy.

## 46. User Experience Rules
- **Activation Success**: "Mini POS activated successfully." -> Immediate transition to billing.
- **Offline**: Absolute silence. No banners, no "Offline mode" warnings.
- **Near Expiry**: Show subtle warning banner 14 days before `validUntil`.
- **Expired**: Show non-dismissable blocking overlay over the Billing UI: "Your license has expired. Please renew." with an action button.

## 47. Edge-Case Matrix
- **Duplicated request**: Idempotent success via `activationRequestId`.
- **Clock forward jump**: May cause premature expiry. User must correct clock and restart.
- **Same-device reactivation**: Succeeds without eating a new license slot.
- **Corrupted authorization**: Fails to `NOT_ACTIVATED`.

## 48. Acceptance Criteria
- **AC-01**: A valid license activates successfully.
- **AC-02**: An invalid license cannot activate.
- **AC-03**: The same license cannot exceed its device limit.
- **AC-04**: Retrying the same activation request is idempotent.
- **AC-05**: A modified authorization fails signature validation.
- **AC-06**: Copied authorization cannot be used by another device (Device Mismatch).
- **AC-07**: Valid authorization permits billing completely offline.
- **AC-08**: Expired authorization blocks billing but permits Product/History/Settings access.
- **AC-09**: Deactivation releases the server binding.
- **AC-10**: Server outage does not interrupt valid offline billing.
- **AC-11**: Crash/restart does not invalidate legitimate authorization.
