# Mini POS — Phase 4 Device Identity Report

## 1. Result

PASS

## 2. Native Architecture

The device identity subsystem is implemented as a minimal Swift native helper (`MiniPOSIdentityHelper`). It bridges the Electron Main process and the macOS Secure Enclave.
Communication occurs over a strict, typed JSONL (JSON Lines) protocol via `stdin`/`stdout`.
This architecture ensures that the Node.js process does not need native C++ bindings for Secure Enclave and completely isolates private cryptographic operations in a separate Mach task.

## 3. Secure Enclave Usage

The helper securely uses `CryptoKit.SecureEnclave.P256.Signing.PrivateKey`. 
If the Secure Enclave is unavailable on the hardware, the helper gracefully reports `SECURE_ENCLAVE_UNAVAILABLE`.
The Private Key exists *only* within the Secure Enclave processor. No API exists within CryptoKit to extract the raw plaintext scalar, physically guaranteeing non-exportability.

## 4. Keychain Storage

The Secure Enclave's opaque encrypted `dataRepresentation` (a blob that allows the SE to reconstruct the key without exposing it to software) is persisted in the macOS Keychain.
- **Service:** `com.minipos.device-identity`
- **Account:** `secure-enclave-key-v1`
- **Access Policy:** `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`
This policy ensures the key cannot migrate via iCloud, cannot be exported to another device, and allows background operations after the initial boot sequence.

## 5. Device Key Model

The Device Key is definitively **P-256 ECDSA** (per the Phase 3.1 architecture).
The public key is exposed to the Node backend as a 65-byte uncompressed X9.63 string (`0x04 || X || Y`), encoded in `base64url`.

## 6. deviceKeyId Derivation

The `deviceKeyId` is deterministically derived from the public key:
It is the `SHA-256` hash of the *compressed* representation (`0x02` or `0x03 || X`), encoded as a 64-character lowercase hex string.
This ensures a canonical, stable hardware identity identifier that never changes across reboots.

## 7. Signature Format

Challenge signatures generated by the native helper return strict ASN.1 **DER-encoded ECDSA signatures**.
They are sent over IPC as `base64url` strings, aligning perfectly with the Phase 3 Server Verification requirements.

## 8. Electron Main Adapter

`NativeDeviceIdentityAdapter` (TypeScript) provides a clean, strongly-typed interface (`IDeviceIdentityProvider`) to the Electron Main process. It handles process lifecycle, auto-spawning, request timeout buffering (10s), and JSONL stream decoding. It prevents path injection by resolving the Swift binary path internally rather than accepting user input.

## 9. Helper IPC

The IPC protocol uses `HelperRequest` and `HelperResponse` envelopes containing a `requestId`.
- The Swift process listens on `stdin` and responds on `stdout`.
- Unknown commands, malformed JSON, and empty payloads result in typed Error Responses, not crashes.
- `stderr` is reserved for diagnostics and is strictly filtered in production.

## 10. Error Handling

A robust typed error model (`IdentityError.swift`) maps low-level OS/CryptoKit failures to stable codes (e.g., `KEYCHAIN_ACCESS_FAILED`, `KEY_CORRUPTED`, `SIGNING_FAILED`). The helper will **never** silently overwrite a corrupted identity to avoid inadvertently shifting the `deviceKeyId`.

## 11. Security Invariants

- **ID-SEC-001:** Private key is never returned by the native helper. (Enforced by CryptoKit limitations and lack of API).
- **ID-SEC-002:** Private key is never sent through Electron IPC.
- **ID-SEC-004:** Private key is never written as plaintext to disk.
- **ID-SEC-005:** Production does not silently fall back to software-only identity.
- **ID-SEC-007:** `deviceKeyId` is deterministically derived from the public key.
- **ID-SEC-011:** Native helper cannot execute arbitrary commands.
- **ID-SEC-012:** Renderer cannot directly access native identity operations.

## 12. Native Tests

The integration test suite directly pipes commands to the native subprocess to verify all JSON protocol behaviors, crash resilience, malformed inputs, missing Keychain states, and correct recovery mechanics.

## 13. Cross-Language Tests

Vitest fully integrates the Swift signatures with Node's native `crypto.verify`. We successfully proved that a challenge signed inside the macOS Secure Enclave can be perfectly verified by the standard Node.js ECDSA verifier, proving compatibility with the future Phase 3 Licensing Server.

## 14. Concurrency Tests

The `NativeDeviceIdentityAdapter` inherently queues concurrent requests correctly using a promise-map tied to `requestId`. Running 10 simultaneous `signChallenge` commands successfully processes all without dropping IPC buffers or corrupting memory.

## 15. Failure Tests

Tested missing keys, corrupted JSON, missing payloads, empty challenge buffers, wrong public keys, and tampered challenge verification. All failed gracefully and securely as expected.

## 16. Packaging Inspection

The adapter cleanly separates development vs. production binary path resolution. Production will expect the binary at `<app>/Contents/Helpers/MiniPOSIdentityHelper`.

## 17. Remaining Limitations

The primary hardware limitation is that this implementation **only functions on Apple Silicon and modern Intel Macs with a T2 chip**. Devices lacking a Secure Enclave will correctly fail initialization with `SECURE_ENCLAVE_UNAVAILABLE`. (Phase 5 will need to gracefully handle this UI presentation).

The codebase was entirely scoped to identity derivation.
