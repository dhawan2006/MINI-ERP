# Mini POS — Phase 3 Cryptographic Protocol Report

## 1. Result

PASS

## 2. Cryptographic Algorithms

- **Server Authorization Signing**: Ed25519 (via Node.js native `crypto`). Generates 64-byte deterministic signatures over the canonical payload.
- **Device Proof Verification**: Ed25519 (via Node.js native `crypto`). Verifies a 64-byte signature generated by the client device over a challenge payload.
- **Canonicalization**: RFC 8785 JSON Canonicalization Scheme (via `canonicalize` package).
- **Encoding**: `base64url` (URL-safe base64 without padding) is strictly enforced for all signatures to prevent format confusion.

## 3. Key Separation

The protocol establishes two mutually exclusive trust hierarchies:
- **Server Keys**: The server owns a secure Ed25519 private key. This key is used strictly for signing authorizations and NEVER leaves the server boundary. The client will store the public counterpart to verify the server.
- **Device Keys**: The device owns a local Ed25519 private key. This key NEVER leaves the device. The server only receives and trusts the device's public key (stored in the `devices` table as `device_key_id`) and uses it to verify proof-of-possession challenges.

## 4. Authorization Format

Signed Authorizations are wrapped in a standard JSON envelope:

```json
{
  "version": "1.0",
  "keyId": "mpos-sign-2026-01",
  "payload": {
    "protocolVersion": "1.0",
    "authorizationVersion": "1.0",
    "licenseId": "uuid",
    "productId": "PROD_1",
    "deviceKeyId": "pub_key_hash",
    "validFrom": "2026-01-01T00:00:00.000Z",
    "validUntil": "2026-12-31T23:59:59.999Z",
    "issuedAt": "2026-06-01T12:00:00.000Z"
  },
  "signature": "base64url_string_86_chars"
}
```

*Note: No private keys are present.*

## 5. Canonicalization

Both the Server Signer and Client Verifier sort and serialize the `payload` object exactly according to RFC 8785. A domain separation string `MINIPOS-AUTHORIZATION-V1:` is prepended to the resulting canonical UTF-8 bytes before feeding it into the Ed25519 primitive.

## 6. Signature Verification

The `AuthorizationVerifier` guarantees a "Fail Closed" design:
- It strictly asserts `version === '1.0'`.
- It requires the `signature` to match exactly `^[A-Za-z0-9_-]{86}$` to prevent padding attacks.
- It parses base64url and throws if malformed.
- It verifies the exact domain-separated canonical payload.
- It refuses fallback to "none" algorithms or incorrect asymmetric algorithms.

## 7. Key Rotation

The signed authorization includes a explicit `keyId` string. The `AuthorizationVerifier` maintains a local map of trusted key IDs. 
- A signature is instantly rejected if the `keyId` is not present in the trusted map.
- Old keys can be retained as verification-only by the client, allowing smooth rotation without breaking existing valid authorizations.

## 8. Challenge Protocol

The server manages proof-of-possession using the `ChallengeService` and `DeviceProofVerifier`:
1. **Creation**: Server generates a 32-byte secure random nonce, creates a JSON payload, and persists it to PostgreSQL `device_challenges` as `PENDING`.
2. **Lifetime**: Challenges default to 60 seconds validity.
3. **Verification**: The device signs the domain-separated (`MINIPOS-DEVICE-CHALLENGE-V1:`) canonical challenge.
4. **Consumption**: The server atomically updates the challenge in Postgres to `CONSUMED` during verification.

## 9. Replay Protection

- **Authorization Replay**: Authorizations are stateless and legitimately reusable during their time window. Replay against a *different* device is prevented because the `deviceKeyId` embedded in the payload must structurally match the local hardware identity in Phase 4.
- **Challenge Replay**: Prevented by PostgreSQL atomic row updates `UPDATE ... WHERE status = 'PENDING' AND expires_at > NOW()`.

## 10. Concurrency

Tested via Vitest (`tests/crypto.test.ts`):
- **100 Simultaneous Consumptions of 1 Challenge**: Exactly 1 attempt succeeded. The other 99 were safely rejected with `CHALLENGE_REPLAYED`.

## 11. Test Vectors

Cross-implementation test vectors (including Server Public Key and expected Signed Authorizations) are automatically generated and dumped to `tests/fixtures/crypto/vector1.json` during the test run. The future Client can use this exact file to prove its own Ed25519 verifier and Canonicalizer are compatible.

## 12. Malformed Input

Fuzz tests confirm safe rejection without server crashes:
- `null` / `undefined` payloads.
- Incorrect types or invalid Base64url padding (e.g. `===`).
- Tampered timestamps or invalid protocol versions.
- Missing signature fields.

## 13. Performance

The cryptography logic runs efficiently. Ed25519 signature generation and verification execute in `<2ms`. Concurrency stress tests resolving 100 verifications and atomic Postgres updates completed in under `30ms`.

## 14. Security Review

- **Q: Can an attacker modify validUntil and still pass?** No, signature covers the entire canonical payload.
- **Q: Can an attacker replace deviceKeyId with another device?** No, payload tampering invalidates the signature.
- **Q: Can an unknown key automatically become trusted?** No, keyId must map to a pre-registered static key in the verifier's trust anchor.
- **Q: Can a reused challenge authenticate twice?** No, Postgres ensures strict `PENDING -> CONSUMED` atomicity.
- **Q: Can renderer code ever receive the server signing private key?** No, the private key is injected strictly into the Node backend.

## 15. Residual Risks

- The `deviceKeyId` binding relies on the Client actually performing the check against its local hardware identity securely.
- While the cryptographic math is sound, exposing a device's signing mechanism to a malicious renderer process could allow an attacker to sign arbitrary challenge bytes. The native isolation in Phase 4/5 is critical to prevent this.
